## Implementation

- Physical-page reference counts in kalloc.c track ownership. New allocations start at one; kfree returns a page to the free list when its count reaches zero. Separate locking protects counts and the free list. A free-page counter supports the next milestone.
- uvmcopy shares mapped physical pages, increments their counts, and replaces writable permissions with a COW flag in parent and child. Untouched lazy pages are skipped. Read-only mapped pages are also shared and reference-counted. TLB flushing makes the changed permissions effective.
- The fault handler retains lazy allocation and adds COW write recovery. An exclusively owned COW page becomes writable directly. A shared page is copied into a new private page and its old reference is released.
- Existing copyout permission checks route writes to COW destinations through the fault handler.
- PTE_COW uses software bit 8. PTE_SWAP, bit 9, is reserved for the later swap implementation; swap has not been implemented yet.
- The guide's wait change was brought forward: save the exit status, free/reap the child, release locks, then copy status into the parent's memory.

## Regression and fix

The first full COW suite failed at sbrkfail. Its final child deliberately accesses a large lazy reservation until physical memory is exhausted, and the parent waits for its failure status. The working diagnosis was that copying status before freeing the child could need a new COW page while the child still held the available memory.

The supplied guide already contains a wait-order change in its later swap section, Step 8g. That change was applied now. The previously failing isolated test and the complete suite subsequently passed. This verifies the practical fix and supports the diagnosis, without an internal allocation trace proving the exact failure site.

The new ordering reaps the child before status copying. Consequently, if that later copy fails, wait returns -1 after the child has already been reaped. Preserve this behavior in the implementation description.

An earlier exec forkbench failed result is also preserved. The file existed; a fresh boot and subsequent repeated sequences ran successfully. No specific cause was established for that earlier launch failure, so do not attribute it to the sbrkfail issue or claim an independently proven fix.
